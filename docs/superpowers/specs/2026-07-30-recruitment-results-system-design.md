# 招新结果中心与预备成员考核台设计规格

日期：2026-07-30
产品：白云 HSD 开发者部落
设计状态：已确认；用户端结果中心已实现，报名表与管理端由独立任务推进
实施边界：用户端结果中心已接入现有 Nuxt 4 / Vue 3 / TypeScript 主站；后端框架、数据库与真实身份系统不在本轮实施范围内

## 1. 目标

将现有“考核结果”占位页升级为受登录保护的个人「结果中心」，同时设计独立的管理端「预备成员考核台」，覆盖以下业务链路：

1. 26 级参与者入库后统一成为预备成员，并享有全平台正常使用权。
2. 预备成员登录后填写最多三个中心志愿，并选择是否接受调剂。
3. 第一志愿为白泽开发中心时，额外选择一个白泽意向方向。
4. 系统按第一志愿将人员划分为白泽、新媒体、拓维策划、人才发展四组。
5. 普通中心通过一轮面试即可成为正式成员；白泽必须依次通过三轮考核。
6. 考核未通过后的调剂在线下完成，系统仅由授权管理员直接录入最终结果。
7. 正式录取后，成员身份、个人中心、中心成员关系与公开成员来源保持一致。

## 2. 已确认的业务规则

### 2.1 志愿

- 第一志愿必填；第二、第三志愿可选，最多填写三个志愿。
- 同一中心不得重复出现在多个志愿中。
- 白泽开发中心只能作为第一志愿，不能作为第二、第三志愿。
- 第一志愿选择白泽后，必须额外选择且只能选择一个白泽意向方向：鸿蒙开发、后端架构、大模型 AIGC、UI/UX 设计、嵌入式开发。
- 白泽方向不占用三个中心志愿名额。
- 第一志愿不是白泽时，第二、第三志愿中也不出现白泽。
- 是否接受调剂为独立必填选项。

### 2.2 分组与权限

- 提交志愿后，预备成员只按第一志愿进入四个中心分组；白泽不按五个子方向再次拆组。
- 联盟总负责人可以查看全部分组与全部预备成员。
- 各中心负责人只查看并操作自己负责的第一志愿分组。
- 个人端只能查看当前登录账号本人的结果。
- 内部备注、操作人、操作时间和变更前后内容不得出现在个人端或公开页面。

### 2.3 考核与转正

- 新媒体中心、拓维策划中心、人才发展中心只有一轮面试。
- 普通中心面试通过后，身份自动更新为该中心正式成员。
- 白泽开发中心依次进行第一轮、第二轮、第三轮考核。
- 白泽上一轮通过后才进入下一轮；第三轮通过后才成为白泽正式成员。
- 后续轮次不得提前编辑或跳过。
- 当前只记录结构化状态与内部备注，不设计分数、排名或公开评语。

### 2.4 调剂

- 调剂沟通和决定在线下完成，系统不设计发起、接收、审批或双确认流程。
- 授权管理员在系统中直接录入线下确认后的最终结果。
- 白泽不能成为调剂目标。
- 普通中心或白泽考核未通过且接受调剂时，只能调剂到新媒体、拓维策划或人才发展中心。
- 不接受调剂或线下决定淘汰时，最终结果为未录取。
- 个人端不展示调剂过程，只展示当前有效结果和最终归属。

## 3. 信息架构

### 3.1 个人端

- 主导航入口改名为“结果中心”，进入 `/member/results`。
- `/member/results` 复用现有登录续接；匿名访问进入 `/login?redirect=%2Fmember%2Fresults`。
- 旧 `/assessment-results` 保留兼容跳转，避免现有入口或收藏失效。
- 页面包含“招新录取”和“阶段考核”两个页签。
- `/member` 同步展示当前身份、三个志愿、白泽意向方向和结果中心入口。

### 3.2 报名端

`/join/apply` 从单一“首选中心”升级为：

- 第一志愿
- 第二志愿
- 第三志愿
- 白泽意向方向，按条件显示
- 是否接受调剂
- 既有基础信息与个人介绍

### 3.3 管理端

新增计划路由 `/admin/recruitment`，仅授权管理角色访问。桌面布局包括：

- 批次信息与核心状态数量。
- 全部人员、白泽、新媒体、拓维策划、人才发展分组导航。
- 姓名/学号搜索。
- 当前阶段、当前结果、是否接受调剂筛选。
- 高密度预备成员表格。
- 右侧成员详情与结果录入抽屉。
- 影响身份操作的二次确认弹窗。

管理端不使用阶段卡片看板，也不在表格行内直接修改结果。

## 4. 个人结果中心设计

### 4.1 页面框架

- 主要验收视口为 `1440 × 1000`。
- 使用标准全站导航和约 `1240px` 内容宽度。
- 页面主体为个人任务页，不使用宣传型大 Banner。
- 主体采用约 `8 / 4` 的双栏结构：左侧当前结果，右侧志愿与负责人。
- 小屏幕按“当前结果 → 志愿 → 负责人”重排为单列，不缩放桌面页面。

### 4.2 招新录取页签

| 状态 | 个人端主标题 | 展示内容 |
| --- | --- | --- |
| 未填写志愿 | 尚未提交志愿 | 前往填写报名表 |
| 等待面试/考核 | 结果待公布 | 当前中心、当前阶段、负责人 |
| 候补 | 当前处于候补状态 | 当前中心、负责人 |
| 普通中心通过 | 已录取 | 正式成员、最终中心、负责人 |
| 白泽第三轮通过 | 已录取 | 白泽开发中心、正式方向、负责人 |
| 调剂后录取 | 已录取 | 只显示最终中心和负责人 |
| 未录取 | 本期未录取 | 克制说明与负责人 |
| 数据未发布 | 结果暂未发布 | 不输出空字段或推测数据 |

个人端禁止出现：

- 确认加入或放弃名额
- 报到时间、报到地点或需携带材料
- 分数、排名或公开评语
- 完整考核历史
- 调剂来源与调剂过程
- 管理员内部备注

### 4.3 阶段考核页签

- 普通中心只显示“面试”和当前状态。
- 白泽只显示当前轮次及其状态。
- 第一轮通过后显示“当前阶段：第二轮考核”，不列出第一轮历史。
- 后台处于线下调剂等待时，个人端统一显示“结果待公布”。

### 4.4 负责人

- 只展示当前中心或最终中心对应的一名负责人。
- 展示经批准的姓名、职务和联系方式。
- 联系方式提供复制动作；不得暴露后台账号或额外个人信息。

## 5. 管理端考核台设计

### 5.1 名单

表格默认列：

- 姓名
- 学号
- 第一志愿
- 白泽方向
- 当前阶段
- 当前结果
- 是否接受调剂
- 最终中心
- 最近更新时间
- 查看/处理

白泽方向只对第一志愿为白泽的记录显示，其余记录显示 `—`。

### 5.2 详情抽屉

抽屉宽度约为桌面视口的 `38%`，包括：

1. 预备成员基础身份。
2. 三个志愿、白泽方向、是否接受调剂。
3. 当前考核录入。
4. 最终结果与最终中心。
5. 仅管理员可见的内部备注。
6. 保存后的联动预览。
7. 取消与保存操作。

普通中心只出现一轮面试控件。白泽显示三轮，但未解锁轮次保持只读。

### 5.3 保存与确认

以下操作需要二次确认：

- 从预备成员变为正式成员。
- 从预备成员变为未录取。
- 直接录入调剂后的最终中心。
- 修改已经生效的最终归属。

确认弹窗展示变更前身份、变更后身份、最终中心、白泽方向以及将被更新的系统模块。

## 6. 状态模型

```text
PREPARATORY
  ├─ 第一志愿普通中心 → INTERVIEW_PENDING
  │    ├─ PASSED → FORMAL_MEMBER
  │    ├─ FAILED + 接受调剂 → OFFLINE_ADJUSTMENT_PENDING
  │    └─ FAILED + 不接受调剂 → NOT_ADMITTED
  └─ 第一志愿白泽 → BAIZE_ROUND_1
       ├─ PASSED → BAIZE_ROUND_2
       │    ├─ PASSED → BAIZE_ROUND_3
       │    │    ├─ PASSED → FORMAL_MEMBER
       │    │    └─ FAILED → OFFLINE_ADJUSTMENT_PENDING / NOT_ADMITTED
       │    └─ FAILED → OFFLINE_ADJUSTMENT_PENDING / NOT_ADMITTED
       └─ FAILED → OFFLINE_ADJUSTMENT_PENDING / NOT_ADMITTED

OFFLINE_ADJUSTMENT_PENDING
  ├─ 录入普通中心 → FORMAL_MEMBER
  └─ 淘汰 → NOT_ADMITTED
```

不存在 `OFFLINE_ADJUSTMENT_PENDING → BAIZE_ROUND_1` 路线。

## 7. 数据职责与未来后端契约

后续数据库至少需要表达以下职责，但本规格不指定数据库产品、ORM 或后端框架：

- 招新批次
- 预备成员档案与登录账号关联
- 志愿申请
- 有序且唯一的中心志愿
- 白泽意向方向
- 考核轮次与当前状态
- 最终归属
- 正式成员关系
- 管理员操作审计

公开成员页面、中心详情和成员风采不得维护重复的成员归属副本；它们应读取统一的正式成员关系，并继续经过既有头像公开规则。

真实后端保存最终结果时必须使用原子事务：任一身份、结果、成员关系或审计写入失败时整体回滚。本轮前端原型只能演示“将同步更新哪些模块”，不得声称已经写入数据库。

## 8. 视觉与无障碍

- 延续品牌深红 `#B1202B`、近黑 `#211F1E`、暖白 `#F4F0EB` 和冷灰 `#F5F6F7`。
- 已录取使用深红标题和低饱和绿色状态标记，不使用庆祝海报、彩带或大面积鲜艳成功色。
- 未录取使用近黑文字和克制的灰红边框，不使用羞辱性或情绪化表达。
- 管理端优先使用表格、边界和间距建立层级，不使用大量圆角悬浮卡片。
- 页签、筛选器、表格操作、抽屉和确认弹窗必须支持键盘操作、可见焦点和清晰的无障碍名称。
- 状态不能只依赖颜色表达，必须同时包含文字。

## 9. 加载、空状态与错误状态

个人端必须覆盖未登录续接、加载中、未提交志愿、结果待公布、候补、已录取、未录取和数据请求失败。

管理端必须覆盖无权限、空分组、无筛选结果、详情加载失败、保存中、保存成功、版本冲突或保存失败。失败后保留用户尚未提交的筛选条件、结果选择和内部备注。

## 10. 验收标准

1. `/member/results` 要求登录并保留安全来源路由续接；旧 `/assessment-results` 兼容跳转。
2. 顶部入口与页面 H1 使用“结果中心”。
3. 个人端具有“招新录取”和“阶段考核”两个页签。
4. 个人端不显示历史时间轴、分数、公开评语、调剂过程或报到信息。
5. 白泽只能作为第一志愿；选择白泽时必须选择且只能选择一个方向。
6. 第二、第三志愿不出现白泽，并且所有志愿不得重复。
7. 普通中心通过一轮面试即可转为正式成员。
8. 白泽必须依次通过三轮，第三轮通过后才能转为正式成员。
9. 调剂目标中不出现白泽，系统不实现线上调剂审批流。
10. 个人端只呈现调剂后的最终结果；后台保留审计信息。
11. 管理端列表、筛选、详情抽屉、二次确认与权限空状态均可被验收。
12. 前端 Mock 必须明确标注不写入真实数据库，不能伪造已完成的全系统同步。

## 11. 非目标

本轮不实现后端 API、数据库迁移、真实账号与角色授权、线上调剂沟通或审批、分数排名、公开评语、消息推送、报到确认、放弃名额、报到安排或批量改变考核结果。
