# HSD 管理员端页面与业务逻辑分析报告

- 分析日期：2026-07-31
- 分析范围：`/admin/**` 管理员端页面、布局、会话守卫、Mock 领域数据、相关单元测试与浏览器行为
- 当前阶段：Nuxt 4 / Vue 3 / TypeScript 前端原型，尚未接入真实身份系统、后端 API、数据库或对象存储
- 结论口径：区分“规格目标”“当前可交互原型”“尚未实现的真实业务能力”

## 1. 结论摘要

当前管理员端已经形成完整的信息架构原型：同一 Nuxt 工程中通过 `/admin/**` 和独立 `admin.vue` 布局与官网隔离，提供 7 个业务域、24 个导航入口、26 个页面路由。页面覆盖工作台、招新考核、组织成员、项目活动、门户内容、媒体资源、系统权限等主要管理场景。

现阶段最有价值的成果是业务边界和页面骨架已经建立：

1. 招新结果采用“内部录入”和“对成员发布”分离的思路。
2. 内容采用“草稿、审核、发布、下架”分离的状态模型。
3. 成员内部资料、公开资料、成长荣誉分区管理。
4. 媒体文件按“对象存储保存原文件，数据库保存元数据和引用”规划。
5. 权限按角色、业务域、动作和数据范围四层表达。
6. 身份、结果发布、权限和删除等高风险操作已在界面上预留二次确认。

但它还不能作为真实管理系统投入使用。当前登录只判断是否存在前端会话，不判断管理员角色；任意满足长度校验的演示账号都可进入管理端。刷新页面后会话丢失。多数“保存、审核、发布、导出、上传、删除”按钮只展示反馈或关闭浮层，没有持久化和跨模块联动。部分关键控件甚至没有绑定数据，却会显示“保存成功”。

因此，当前管理员端应被定义为：**信息架构和交互语义较完整的前端原型，不是具备真实业务闭环的管理系统。**

## 2. 架构与访问边界

### 2.1 当前架构

```text
同一 Nuxt 应用
├── 官网与成员端
│   ├── 默认布局
│   ├── 公开导航
│   └── /member/** 个人任务页面
└── 管理员端
    ├── /admin/** 路由命名空间
    ├── admin.vue 独立布局
    ├── 固定侧栏 + 顶栏 + 高密度工作区
    └── TypeScript Mock 数据
```

管理布局负责：

- 渲染 7 个可展开导航分组。
- 根据当前路由匹配导航激活态和顶栏面包屑。
- 展示“联盟总负责人”原型身份。
- 提供返回官网和退出登录。
- 隔离官网主导航，避免管理入口混入公开浏览体验。

主要代码：

- [`app/layouts/admin.vue`](../app/layouts/admin.vue)
- [`app/data/admin-platform.ts`](../app/data/admin-platform.ts)
- [`app/middleware/auth.global.ts`](../app/middleware/auth.global.ts)
- [`app/stores/session.ts`](../app/stores/session.ts)

### 2.2 当前认证与授权事实

当前全局守卫仅检查 `session.isAuthenticated`：

```text
访问 /admin/**
  ├── 未登录：跳转 /login?redirect=原地址
  └── 已登录：直接放行
```

实际没有以下能力：

- 没有管理员身份字段。
- 没有当前角色和数据范围。
- 没有路由级权限元数据。
- 没有按钮级动作权限判断。
- 没有服务端会话或 Cookie。
- 没有 API 层二次授权。
- `/admin/forbidden` 只是静态演示页，当前不会由权限判断自动进入。

浏览器核验结果：

- 使用普通演示账号 `member-demo` 和任意 6 位密码，可以进入 `/admin/content`。
- 管理 URL 刷新或直接打开后，Pinia 内存会话被重置，再次跳回登录页。

这意味着当前“管理员端受保护”只是一层页面体验控制，不构成安全边界。

## 4. 核心业务逻辑

### 4.1 工作台

工作台定位为任务入口，而不是数据大屏。它按以下优先级组织信息：

1. 四个可点击核心指标。
2. 按 `urgent → warning → normal` 排序的待办。
3. 四个中心的招新进度。
4. 内容发布动态。
5. 媒体与存储状态。
6. 最近操作记录。
7. 快捷新建菜单。

目标逻辑是“从指标或待办跳转到已经带筛选条件的业务列表”。当前链接确实带查询参数，例如：

- `/admin/recruitment?result=待处理`
- `/admin/content?status=待审核`
- `/admin/media?view=storage`

但目标页面没有读取 URL 查询参数。浏览器核验中，访问 `/admin/content?status=待审核&create=flash` 后仍显示全部 4 条记录，筛选仍为“全部状态”，新建抽屉也没有打开。因此目前工作台只能完成导航，不能恢复任务上下文。

另有一处状态命名不一致：工作台“待发布内容”链接使用 `status=待发布`，但内容领域类型只有“草稿、待审核、已发布、已下架”，没有“待发布”。接入真实查询前需要先统一“审核通过待发布”是否为独立状态。

### 4.2 招新与考核

#### 目标业务链路

```text
创建招新批次
  → 接收报名资料
  → 按第一志愿分组
  → 执行对应中心考核
  → 保存内部结果
  → 联盟总负责人集中检查
  → 批量发布
  → 更新个人结果中心
  → 更新正式成员关系和中心归属
  → 记录审计日志
```

#### 志愿和考核规则

- 最多三个不重复中心志愿。
- 白泽只能作为第一志愿。
- 选择白泽必须同时选择一个白泽方向。
- 白泽方向不占中心志愿名额。
- 白泽名单只按中心分组，不按方向继续拆组。
- 新媒体、拓维策划、人才发展只进行一轮面试。
- 白泽依次进行第一轮、第二轮、第三轮，后续轮次不得提前编辑。
- 调剂在线下完成，系统只录入最终普通中心或未录取。
- 白泽不能作为调剂目标。

#### 当前数据与页面行为

`ADMIN_CANDIDATES` 提供 8 条候选人 Mock，覆盖预备成员、正式成员、未录取、白泽三轮、普通中心面试、线下结果待录入等状态。筛选支持第一志愿、姓名/学号、阶段、结果、调剂意愿的组合条件。

概览指标中的“预备人员”当前直接取本批次全部 8 人，其中实际还包含 2 名正式成员和 1 名未录取人员。页面副文案写的是“本批次全部人员”，但主标签会让管理员误以为 8 人都仍是预备成员，需要改为“批次人员”或按身份真实统计。

线下最终结果录入是目前最接近真实业务更新的交互：选择普通中心后确认，会把当前候选人的身份设为正式成员、阶段设为已结束、结果设为已录取，并在当前页面内存中更新。

但是常规考核录入存在关键缺口：

- 白泽各轮 `select` 只有 `:value`，没有 `v-model` 或变更事件。
- 普通中心面试结果同样没有绑定数据。
- 点击确认保存后只更新内部备注和时间，不更新轮次或面试结果。
- 页面仍显示“结果已保存到当前 Mock 会话”。

浏览器实测将林同学第二轮从“待公布”改为“通过”后，控件立即恢复“待公布”；确认保存后仍显示“结果已保存”。这是当前最明显的“反馈与真实状态不一致”。

结果发布页将“阶段为已结束”的候选人判定为可发布，支持勾选和二次确认。发布后只设置页面级 `published = true`，不会真正更新：

- 用户端结果中心。
- 成员身份数据源。
- 中心成员关系。
- 公开名录。
- 操作日志。

### 4.3 组织与成员

成员业务被拆为三层：

```text
内部资料：学号、年级、身份、中心、联系方式、账号状态
公开资料：公开名称、职责、介绍、头像公开状态、资料审核状态
成长荣誉：项目、活动、荣誉和审核结果
```

公开资料遵循以下隐私规则：

- 头像已上传且允许公开时才输出真实头像。
- 未上传或不公开时使用 HSD 默认头像。
- 不公开头像的原始地址不得进入公开页面。
- 荣誉必须审核通过并由成员选择公开。
- 核心人员从统一成员关系中选择，不复制成员基础资料。

当前 `useMemberRepository` 做了一层有限的数据投影：当前演示成员在个人资料 Store 中修改方向、简介和头像后，可映射到公开人员数据和管理员成员列表。其他成员仍来自静态数组。

当前缺口：

- 成员详情表单多数使用 `:value`，没有形成可提交草稿。
- “保存资料”和“调整身份”确认不会更新成员模型。
- 核心人员顺序、添加、编辑、公开切换均为展示。
- 中心配置按钮无业务行为。
- 荣誉审核选择和说明不写回审核记录。
- 招新录取不会更新管理员成员列表；候选人与正式成员仍是两套独立 Mock 数据。

### 4.4 项目与活动

项目目标字段包括：参与中心、成员、状态、媒体资产、竞赛成果和首页推荐。活动目标字段包括：时间、地点、容量、报名截止、负责人、报名字段、候补/取消状态和名单导出。

项目、活动和门户内容共用 `AdminRecordWorkspace`：

```text
搜索和筛选
  → 列表
  → 打开编辑抽屉
  → 编辑标题、分类、摘要
  → 对外预览
  → 保存草稿或提交状态
```

通用工作区目前只操作一份选中记录的浅拷贝。关闭抽屉后修改不会回写源列表，新建记录也不会加入列表。项目和活动的领域字段没有进入编辑器，因此项目成员、中心、素材、成果、活动时间、容量和报名字段目前只能查看，不能维护。

活动报名名单当前是 3 条页面内静态数据；搜索、活动筛选、状态筛选、报名详情、字段配置和导出没有实现。

### 4.5 内容与门户

规格中的内容状态机为：

```text
草稿 → 待审核 → 已发布 → 已下架
  ↑        │                    │
  └────────┘                    └→ 草稿
```

代码中的 `canTransitionContent` 正确表达了允许路径：

- 草稿 → 待审核。
- 待审核 → 草稿或已发布。
- 已发布 → 已下架。
- 已下架 → 草稿。
- 禁止草稿直接发布。

但页面没有使用该函数。通用编辑器使用简单二元判断：

- 当前为“待审核”时变为“已发布”。
- 其他任何状态都变为“待审核”。

因此已发布内容会被改回待审核，而不是进入已下架；已下架也会直接进入待审核。页面实现与领域状态机不一致。

首页配置采用固定槽位：

| 槽位 | 容量 |
| --- | ---: |
| HSD 快讯 | 1 |
| 推荐新闻 | 3 |
| 精选项目 | 4 |
| 近期活动 | 3 |
| 媒体专题 | 1 |
| 推荐资源 | 3 |

这一设计确保管理员只能替换和排序内容，不能破坏官网已经确认的信息架构。当前只实现槽位、占用量和按钮外观，替换、选择、拖拽排序、容量校验和用户端预览均未实现。

Banner 和帮助中心均已提供页面骨架。Banner 尚未连接已审核素材库，也没有视觉、文案、跳转、审核和启停的编辑流程。

### 4.6 媒体与资源

#### 目标素材链路

```text
选择文件
  → 浏览器分片直传对象存储
  → 服务端保存元数据
  → 异步缩略图 / 转码 / EXIF 清理 / 病毒扫描
  → 人工审核
  → 可使用
  → 被 Banner、项目、活动、画廊等内容引用
```

公开可选条件已经在 `canSelectAsset` 中明确：

```text
processingStatus === ready
且 reviewStatus === approved
```

素材库可按名称、作者、替代文本、类型和处理状态筛选，并能查看处理状态、审核状态、替代文本和引用位置。上传队列覆盖等待上传、上传中、处理中和失败。

当前所有上传进度都是静态数据；选择本地文件、分片上传、重试、审核、保存元数据、移入回收站和引用检查均未实现。素材详情直接引用静态对象，编辑替代文本会修改浏览器内存中的原对象，但没有明确保存边界，也不会产生审计记录。

#### 学习资料

学习资料当前支持以下领域信息：

- 标题、分类、格式和说明。
- 公开、登录成员、指定中心三种访问范围。
- 草稿、待审核、已发布三种状态。
- 版本号、文件名、大小、上传人、时间和当前/历史状态。

规格中还要求“仅管理员”第四种访问范围，当前类型中尚未包含。上传新版本、设置当前版本、病毒扫描、Office 转 PDF、PDF 预览、短时签名下载和访问日志都只是说明文字。

### 4.7 系统与权限

权限模型表达为：

```text
角色
  × 业务模块
  × 动作（查看、新建、编辑、审核、发布、导出）
  × 数据范围（全联盟、所属中心、媒体与门户、内容草稿）
```

当前预置角色：

- 联盟总负责人：全部业务和动作。
- 中心负责人：所属中心的招新、成员、项目活动等。
- 媒体管理员：内容、媒体、资源和部分查看权限。
- 内容编辑：创建和编辑内容，不具备发布权限。

权限数据和单元测试可以正确判断示例权限，但没有连接到会话、路由、按钮或数据查询。角色矩阵中的复选框使用 `:checked` 展示，点击不会更新权限模型；确认保存也不会产生变化。

操作日志已经包含执行人、角色、模块、动作、对象、前后状态、结果、时间、IP 和设备，并支持关键词、模块和结果筛选。它仍是静态 Mock，其他页面的操作不会向日志追加记录。

回收站展示 30 天保留和恢复/永久删除入口，但没有引用检查、确认层、恢复、永久删除或审计更新。

## 5. 跨域数据关系

真实系统需要围绕统一领域数据建立联动，而不是继续维护互不相干的页面数组。

### 5.1 招新录取联动

```text
RecruitmentCandidate
  → AssessmentResult
  → PublicationBatch
  → MemberIdentity
  → CenterMembership
  → MemberResultCenter
  → PublicMemberProjection
  → AuditLog
```

这组更新应在后端原子事务中完成。任一步失败都不能留下“结果已发布但成员关系未建立”之类的半完成状态。

### 5.2 内容发布联动

```text
ContentRevision
  → ReviewDecision
  → PublishedContent
  → HomepageSlotReference（可选）
  → PublicList / Detail
  → AuditLog
```

保存草稿、提交审核、审核通过、发布和下架应是不同 API 与权限动作。

### 5.3 媒体引用联动

```text
StoredObject
  → AssetMetadata
  → ProcessingJobs
  → ReviewDecision
  → AssetReference
  → Public CDN Variant
```

删除素材前必须查询引用；被公开内容使用的素材不能直接永久删除。

### 5.4 当前数据源分散问题

当前存在多组互不联动的 Mock：

- `ADMIN_CANDIDATES`：招新候选人。
- `ADMIN_MEMBERS`：管理员成员列表。
- `PUBLIC_MEMBERS` / `CORE_PEOPLE`：公开成员数据。
- `member-results.ts`：用户结果中心。
- `ADMIN_DASHBOARD_*`：工作台统计和待办。
- `ADMIN_AUDIT_RECORDS`：操作日志。

目前只有当前演示成员的个人资料通过 `useMemberRepository` 做有限投影。正式开发前应先确定统一实体、主键、关系和读模型，否则页面接入 API 后很容易出现人数、身份、中心归属和公开状态互相冲突。

## 6. 实现差距与优先级

### P0：真实开发前必须先解决

1. **建立真实认证和管理员授权。** 当前任意演示登录都能进入管理员端；必须引入服务端会话、管理员角色、动作权限、中心数据范围和 API 二次校验。
2. **修复会话持久性。** 当前刷新即退出；需要安全 Cookie 或服务端 Session，不能依赖 Pinia 内存布尔值。
3. **消除“假保存成功”。** 考核轮次没有写入却提示成功；所有保存反馈必须以真实提交结果为准。
4. **建立统一招新、成员、中心、用户结果和审计事务。** 结果发布必须真正形成跨域一致更新。
5. **统一内容状态机。** 页面必须使用领域状态规则，拆分保存、提交审核、发布和下架动作。

### P1：首个可用管理版本需要完成

1. 让页面读取并同步 URL 查询参数，使工作台待办跳转真正带入筛选和新建上下文。
2. 为列表补齐分页、批量操作、加载、错误、空数据、无权限和并发冲突状态。
3. 把角色矩阵接入可编辑模型，并在前端控制路由和动作可见性；后端仍需再次校验。
4. 完成成员资料、核心人员、中心配置和荣誉审核的真实表单与审核流。
5. 完成项目、活动和内容的领域专用编辑页，避免通用编辑器只维护标题和摘要。
6. 完成素材上传、处理、审核、引用检查和回收站流程。
7. 完成学习资料四级访问范围和不可覆盖的版本历史。
8. 所有详情抽屉统一实现焦点进入、Escape 关闭、背景滚动锁定和焦点返回。

### P2：可用后继续完善

1. 将工作台指标从静态数字改为后端聚合读模型。
2. 增加审计日志导出、保留策略和敏感字段脱敏。
3. 增加并发编辑版本号、离开未保存提示和冲突合并策略。
4. 补齐管理端窄屏紧急操作体验。
5. 增加管理动作的通知、失败重试和可观测性。

## 8. 测试与核验证据

本次分析覆盖：

- 26 个 `app/pages/admin/**` 页面。
- 7 个管理员领域数据模块。
- 10 个管理员相关测试文件。
- 管理布局、全局守卫、登录、Pinia 会话和成员数据仓库。
- 管理平台设计规格、实施计划、项目需求文档和设计基线。

验证结果：

- 管理相关 7 个单元测试文件全部通过，共 23 项测试通过。
- gstack 浏览器验证了登录跳转、管理导航隔离、工作台、URL 上下文、内容列表、招新考核抽屉和保存行为。
- 页面运行时无浏览器控制台错误。
- 本地开发服务器存在文件监听数量限制，浏览器核验改用现有 Nuxt 生产构建运行；该环境问题不改变上述业务逻辑结论。

现有单元测试主要验证数据函数和静态规则，尚未覆盖以下高风险事实：

- 普通登录账号可以进入管理员端。
- 刷新后管理会话丢失。
- 工作台查询参数未被目标页面消费。
- 考核轮次修改未写入但显示保存成功。
- 内容页面绕过 `canTransitionContent`。
- 权限矩阵勾选不更新角色权限。
- 发布动作不产生跨域联动和审计记录。

## 9. 最终判断

管理员端的页面范围、信息架构、设计语义和核心业务规则已经足够支撑后续开发，不需要重新设计整个平台。下一阶段不应继续扩充静态页面数量，而应先建设三条底层主线：

1. 真实认证、RBAC 和数据范围授权。
2. 招新到正式成员的统一领域模型与事务。
3. 内容、素材和资源的审核发布基础设施。

完成这三条主线后，现有 26 个页面可以分批接入真实 API；否则继续为单页补按钮和 Mock 状态，只会扩大数据不一致和“看似可操作、实际无落地”的范围。
